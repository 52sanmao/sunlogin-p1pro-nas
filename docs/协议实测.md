# P1Pro 本地协议实测记录

> 全部结论来自对真机（P1Pro，固件 2.0.4）的实际请求，不是厂商文档抄录。
> 标注"实测"的地方都附了真实响应；标注"推测"的地方会写清楚依据。

---

## 一、通道

| 通道 | 地址 | 鉴权 | 可用性 |
|---|---|---|---|
| **本地直连** | `http://<IP>:6767/plug?_api=…` | `time` + `key` | ✅ 本项目使用，单次约 **34 ms** |
| 云端同构 | `https://slapi.oray.net/plug?_api=…` | OAuth token | 需要登录态，本项目不依赖 |

| TCP 4399 | — | — | ❌ TCP 半开，零响应 |
| `iots-ps03-g2.oray.net:12312` | — | — | ❌ 仅设备与服务端之间的长连接 |

## 二、鉴权

```
GET /plug?_api=<方法>&<参数>&time=<MMddHHmm>&key=<MD5(sn + "==smart-plug==" + time)>
```

实测确认的几点：

1. **`get_plug_sn` 与 `get_plug_version` 之外的接口都要 key**；`get_plug_sn` 完全免鉴权。
2. **`time` 只是 MD5 的盐，固件不校验时效**。
   `time=01010000`、`time=abcdefgh` 只要 key 与之匹配都能通过。
   （这既意味着"算一次 key 永久有效"，也意味着**别依赖它做安全边界**。）
3. **本地不需要传 `sn`**，SN 由固件自己知道。
4. 鉴权校验发生在**方法查找之前** —— 错 key + 不存在的 `_api` 仍然只返回 `3`，不返回 `1`。

本项目仍用实时 `MMddHHmm`：万一哪天固件开始校验时间窗口，
静态盐会让整套逻辑瞬间全废，而正确做法只多花不到 10 µs。

## 三、20 个方法

### 只读（10 个）

| # | `_api` | 参数 | 实测返回 |
|---|---|---|---|
| 1 | `get_plug_sn` | **无（免鉴权）** | `{"sn":"024389379975","type":"P1Pro","result":0}` |
| 2 | `get_plug_status` | 无 | `{"response":[{"index":0,"status":1},…×4],"led":1,"def_st":2,"result":0}` |
| 3 | `get_plug_electric` | 无（`current_unit` 无效） | `{"vol":229114,"curr":136000,"power":23585,"result":0}` |
| 4 | `get_plug_info` | 无 | `{"name":"PLUG-P1Pro-9975","sn":"…","mac":"64:e8:…","version":"2.0.4","led":1,"def_st":2,"result":0}` |
| 5 | `get_plug_version` | 无 | `{"version":"2.0.4","version_num":204,"develop_num":0,"result":0}` |
| 6 | `get_plug_wifi` | 无 | `{"ip":"192.168.0.15","mask":"255.255.255.0","gw":"192.168.0.1","ssid":"FAST_EDCE","password":"","result":0}` |
| 7 | `get_plug_name` | 无 | `{"name":"PLUG-P1Pro-9975","result":0}` |
| 8 | `plug_upgrade_status` | 无 | `{"rate":0,"status":0,"result":0}` |
| 9 | `plug_timer_get` | `index` | 有定时：`{"timer":[{…}],"result":0}`<br>**无定时：只有 `{"result":0}`，没有 `timer` 字段** |
| 10 | `plug_cntdown_get` | `index` | 有：`{"count":7200,"remain":7198,"action":0,"result":0}`<br>无：`{"count":0,"remain":0,"action":255,"result":11}` |

> ⚠️ `plug_timer_get` 返回 `result:0` **不等于**"有定时"。必须判断响应里是否存在 `timer` 字段。
> 只判 `result` 会得到"四个口都有定时"的错误结论。

> ⚠️ `current_unit` 参数**完全无效**：不传、传 `mA`、传 `A`，`curr` 都是同一个值。

### 写 / 动作（10 个）

| # | `_api` | 参数 | 说明 |
|---|---|---|---|
| 11 | `set_plug_status` | `index`(0 起), `status`(1/0) | 单口通断 |
| 12 | `set_all_plug_status` | `status`(1/0) | 四口一起，**没有 index 参数** |
| 13 | `set_plug_led` | `enabled`(1/0) | 指示灯 |
| 14 | `set_plug_dfltstat` | `default`（**0 关 / 2 开**） | 断电记忆。不是布尔，传 `1` 无效 |
| 15 | `set_plug_name` | `name`（≤32 字符） | 改设备名，写入固件 |
| 16 | `plug_cntdown_add` | `index`, `action`(1 开/0 关), `count`(秒) | 设倒计时 |
| 17 | `plug_cntdown_del` | `index` | 取消倒计时 |
| 18 | `plug_timer_add` | `index`, `timer`（**JSON 字符串**） | 新增定时 |
| 19 | `plug_timer_del` | `index`, `timer`(分钟数), `repeat` | 删除定时 |
| 20 | `plug_timer_set` | `index`, `timer` | ⚠️ **形同虚设**，参数齐全也恒返回 `9` |

**参数名的确认方法**（不产生副作用）：给方法传越界 `index=9`。

- 参数名不对 / 缺参 → 返回 `4`
- 参数齐了、只是索引越界 → 返回 `5`

例如 `plug_cntdown_add`：

```
index=9                    → 4
index=9&count=60           → 4      （还缺 action）
index=9&action=0           → 4      （还缺 count）
index=9&action=0&count=60  → 5      ✅ 参数名全对，仅索引越界
```

所以 `plug_cntdown_add` 的三参数是 `index` + `action` + `count`，一个都不能少。

## 四、返回码

| 码 | 含义 | 触发方式（实测） |
|---|---|---|
| `0` | 成功 | — |
| `1` | 未知方法 | `_api=get_plug_status_x` |
| `3` | 鉴权失败 | 不带 time/key，或 key 算错 |
| `4` | 缺必需参数 | `set_plug_status` 不传 index |
| `5` | 索引越界 **或取值非法** | `index=9`；`status=7` 也返回 5（不是 9） |
| `9` | 目标不存在 / 参数冲突 | 删除不存在的定时；`plug_timer_set` 恒 9 |
| `11` | 该口没有倒计时 | `plug_cntdown_get` 空态，同时 `action=255` |

## 五、字段单位

全部是"千分之一"。

| 字段 | 实际单位 | 换算 | 示例 |
|---|---|---|---|
| `vol` | **mV** | ÷1000 → V | `229114` → 229.11 V |
| `curr` | **µA** | ÷1000 → mA；÷1e6 → A | `136000` → 136 mA |
| `power` | **mW** | ÷1000 → W | `23585` → 23.59 W |
| `status` | 1 开 / 0 关 | — | — |
| `led` | 1 开 / 0 关 | — | — |
| `def_st` | 0 未知 / 1 关 / **2 开** | — | `2` = 断电记忆已开启 |

> ⚠️ **不要用 `P = U × I` 反推校验**。
> 实测 `136 mA × 229.1 V = 31.2 VA`，而 `power = 23.59 W`，功率因数约 0.76（低负载时会更低，空载可到 0.39）。
> `curr` 是**视在电流**，`power` 是有功功率，两者物理上就不同，不能互推。

## 六、定时（timer）

`plug_timer_add` 的 `timer` 必须是 **JSON 字符串**（会被 URL 编码）：

```json
{"time": 1410, "action": 1, "repeat": 127, "enabled": 1}
```

| 字段 | 语义 |
|---|---|
| `time` | **UTC 0 点起的分钟数**（0–1439）。⚠️ 不是本地时间 |
| `action` | 1 打开 / 0 关闭 |
| `repeat` | **星期位图**，bit0 = 周日 … bit6 = 周六 |
| `enabled` | 写入时被固件**强制改成 1**，传 0 无效 |

### 时区换算

```
device_minutes = (local_hour * 60 + local_minute - tz_offset_minutes) % 1440
```

东八区 `tz_offset_minutes = 480`：

| 本地时间 | 本地分钟 | 设备要填 |
|---|---|---|
| 00:01 | 1 | 961 |
| 07:30 | 450 | **1410** |
| 12:00 | 720 | 240 |
| 23:59 | 1439 | 959 |

**填错的后果不是报错，而是这个定时永远不触发。**
实测对照：按 UTC 挂的定时准点动作，按本地时间直接填的定时到了钟点毫无反应。

### repeat 常用值

| 值 | 十六进制 | 含义 |
|---|---|---|
| `127` | 0x7F | 每天 |
| `62` | 0x3E | 工作日（周一~周五） |
| `65` | 0x41 | 周末（周日 + 周六） |
| `0` | 0x00 | 仅一次 |

### 增删往返（实测）

```
add index=3 timer={"time":1439,"action":0,"repeat":0,"enabled":1}
  → {"result":0}

get index=3
  → {"timer":[{"time":1439,"action":0,"repeat":0,"enabled":1}],"result":0}

add index=3 timer={"time":1400,"action":1,"repeat":62,"enabled":1}
  → {"result":0}                     ← 支持同一口多条

get index=3
  → {"timer":[{"time":1400,…},{"time":1439,…}],"result":0}

del index=3 timer=1439 repeat=0
  → {"result":0}                     ← 按 (time, repeat) 定位删除

del index=3 timer=1400 repeat=62
  → {"result":0}

get index=3
  → {"result":0}                     ← 干净，连 timer 字段都没了
```

删除时 `repeat` 必须与原定时**完全一致**，因为定位键是 `(time, repeat)` 组合。

## 七、倒计时（countdown）

```
add index=3 action=0 count=7200
  → {"result":0}

get index=3
  → {"count":7200,"remain":7200,"action":0,"result":0}
  （2 秒后）
  → {"count":7200,"remain":7198,"action":0,"result":0}   ← remain 每秒递减

del index=3
  → {"result":0}

get index=3
  → {"count":0,"remain":0,"action":255,"result":11}      ← 空态
```

- `count` 是设定值，`remain` 是剩余秒数，`action` 是到点后的动作（1 开 / 0 关）
- 空态用 `result:11` + `action:255` 双重标记，**不能只看 `count == 0`**
  （设一个 0 秒倒计时在语义上不成立，但读空态时必须两个条件一起判）

## 八、被三方文档写错的地方

逐条实测核对结果：

| 三方文档的说法 | 实测 |
|---|---|
| HTTP/1.1 | ❌ 恒为 **HTTP/1.0**，`Server: esp8266-httpd/0.3`，`Connection: close` |
| 服务器需要传 `sn` | ❌ 本地不需要，传错也不影响 |
| `vol` 单位是 V | ❌ 是 **mV** |
| `index` 范围 0–7 | ❌ 本机 0–3，越界返回 `5` |
| 只能 GET | ❌ POST 同样可用 |
| 共 19 个接口 | ❌ 实际 **20 个**（漏了 `set_plug_name`） |
| 需要 8080 端口变种 | ❌ 只有 6767 对 `/plug` 有响应 |
| `plug_timer_set` 可整体覆盖 | ❌ 恒返回 `9`，不可用 |
| 鉴权 key 有 1 分钟有效期 | ❌ `time` 只是盐，**不校验时效** |

## 九、最小可跑示例

```python
import hashlib, json, time, urllib.parse, urllib.request

IP = "192.168.0.15"

# 必须绕开系统代理，否则开着代理软件时内网请求会被转发出去
opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))

def call(method, **params):
    sn = json.loads(
        opener.open("http://%s:6767/plug?_api=get_plug_sn" % IP, timeout=3).read()
    )["sn"]
    stamp = time.strftime("%m%d%H%M")
    key = hashlib.md5((sn + "==smart-plug==" + stamp).encode()).hexdigest()
    q = dict(params, _api=method, time=stamp, key=key)
    url = "http://%s:6767/plug?%s" % (IP, urllib.parse.urlencode(q))
    return json.loads(opener.open(url, timeout=3).read())

print(call("get_plug_status"))     # {"response":[{"index":0,"status":1},…],"result":0}
print(call("get_plug_electric"))   # {"vol":229114,"curr":136000,"power":23585,"result":0}

# 北京时间 07:30 关闭 S1，每天
call("plug_timer_add", index=0,
     timer=json.dumps({"time": 1410, "action": 0, "repeat": 127, "enabled": 1}))
```

## 十、性能与并发

| 项目 | 实测 |
|---|---|
| 单次请求往返 | **24–34 ms**（同一交换机） |
| 连续请求 | 间隔 < 30 ms 时偶发 `WinError 10054`（设备主动 RST），**35 ms 以上稳定** |
| 并发 | **不支持**。同时发两个请求必有一个失败 |
| 一次状态+电量采集 | 约 70 ms |

所以任何客户端都必须**串行化**，并且请求之间留至少 35 ms。
本项目在 `protocol.py` 里用全局锁 + `MIN_GAP_SECONDS = 0.035` 保证这一点。
